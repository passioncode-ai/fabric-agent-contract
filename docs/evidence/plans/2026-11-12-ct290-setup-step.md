# Design 2026-11-12: a setup step and its gates (CT-290)

**Status:** the design CT-290 owes by 2026-11-19, drafted for the requester (passioncode-platform, PLAT-148) and the
first reader (Fabric Dashboards, FD-208 and FD-209) to confirm; the decision follows with the organization slice's next
cut. Rules are proposals numbered `SS-*`; the DEC may keep or renumber them.

**Asked by:** passioncode-platform's board message `0635ad44` (thread `638a2e88`, 2026-11-11), from its report
`docs/reports/2026-11-11-agent-first-setup/README.md` at `32a81ef`, sections 5.2 and 5.3. Fabric Dashboards waits on it
for its Setup card by layers (board message `08f94ef9`, 2026-11-12: two working days after the decision).

**The need.** The launcher's doctor, the organization product's setup status, the host agent's receipts and the PM agent
each report the steps of setting something up for a person in their own form, so a surface that shows one ordered list
(Fabric Dashboards' Setup card, the coding agent's session before any app is installed) maps each of them. The report
asks for one record every owner emits and one closed list of the steps only a person can take.

## What the contract has today

| Where | What it has | What is missing |
| --- | --- | --- |
| [service](../../specification/service.md#actions) AP-4 (DEC-0121, DEC-0142) | an action's `humanStep`: `sign-in`, `consent`, `payment`, `secret`, `spend-above-limit`, `passkey`, `comparison`, and `human-step-required` with the step's direct link | no setup step, no order, no state; no one-time code, no attestation, no publication |
| [service](../../specification/service.md) commands | `doctor` and `update`, whose output is the product's own text | no structured step a reader can order |
| [page links](../../specification/service.md#page-links) PL-4 (DEC-0123) | a service's own page handed over as its `fabric-dashboards://` open link | the link a person's setup step carries |

## The design

**SS-1, the step record `setup-step/1`.** One object per step, every member closed:

| Member | Rule |
| --- | --- |
| `id` | stable within its layer and owner, `[a-z0-9][a-z0-9._-]{0,127}` (`l1.apps.switchboard`, `l3.dpia.attest`) |
| `layer` | `computer`, `places`, `organization` or `people` |
| `order` | a positive integer, the step's position in its layer; two steps of one answer never share it |
| `title` | what the step is, one line in the person's language (added to the report's list: a surface needs a name to show) |
| `state` | `done`, `next`, `working` (an agent is on it), `waiting` (on other steps or a date, `waitsOn`), `blocked` (a failure, `why`) |
| `waitsOn` | with `waiting` only: 1 to 16 step ids of the same answer, or a date (`until`, RFC 3339) |
| `actor` | `agent`, `person` or `machine` (a program or a machine's own agent, a node enrolling) |
| `gate` | present exactly when `actor` is `person`: one gate of SS-3 |
| `why` | one line in the person's language: what the step gives, and for a person's step why no route avoids it; required for a person's step and for `blocked` |
| `door` | present exactly when `actor` is `agent`: the MCP tool (`name`) or the command (`argv`, no secret, no home folder) that takes it |
| `link` | for a person's step: one link that passes it, an https URL or a registered dashboard's open link (PL-4) |
| `evidence` | with `done` only: what proved it, 1 to 8 references (a check id, a receipt, a record id), never content |

**SS-2, a layer's answer `setup-layer/1`.** An owner answers its layer as `{type: "setup-layer/1", layer, owner,
generatedAt, steps}`, `owner` its service key (`id.instance`), `steps` 0 to 256 `setup-step/1` records. How a reader asks
is the owner's own door (the launcher's `setup --plan --json`, the organization product's setup status, a host agent's
receipt, an MCP tool), each named in the owner's descriptor; the answer's shape is this one everywhere.

**SS-3, one gate vocabulary.** AP-4's `humanStep` and a setup step's `gate` are one closed list: AP-4's seven
(`sign-in`, `consent`, `payment`, `secret`, `spend-above-limit`, `passkey`, `comparison`) and three the report adds:
`one-time-code` (the person types a code sent to them), `attest` (the person signs a statement only they can make) and
`publish` (the person approves something going to people outside the agent's reach). The report's `typed-secret` is
AP-4's `secret` (typed in or handed out); its "spend above a limit is a consent" is not taken: AP-4 keeps
`spend-above-limit` apart, since the money limits are their own rule (L0, L1, a key's ceiling). Every other step is an
agent's or a machine's. A service action declared `gate: human` may name any of the ten.

**SS-4, the reader.** A surface renders the owners' answers in layer order (`computer`, `places`, `organization`,
`people`), then by `order`; it computes no state, merges no steps and invents none; a layer whose owner did not answer
is shown as not read, never as done. A person's view may fold `done` steps and show only the next one (the report's
section 5.4); the agent reads the whole list.

**SS-5, the sheet.** At the start of a run, the steps whose `actor` is `person`, in order, are the run's sheet: each
gate one line with its `why`, so a person can take the steps that wait on nothing at once.

**SS-6, no secret and no person in a record.** No member carries a secret, a home folder or a person's name or address;
`title` and `why` are product text and follow the copy rules of each product's own text.

## What the DEC owes

- **Schemas:** `setup-step.schema.json` (SS-1), `setup-layer.schema.json` (SS-2); `service-actions-extension.schema.json`'s
  `humanStep` gains `one-time-code`, `attest`, `publish` (SS-3), with `human-step-required`'s list in AP-4.
- **Rules:** one `FAC-SEM` code on a layer's answer: ids once, `order` once, `gate` exactly for a person's step, `door`
  exactly for an agent's, `waitsOn` naming steps of the same answer and never a cycle, `evidence` only on `done`, `why`
  where required, no secret or home folder in `door`.
- **Vectors:** a layer with each state and actor; a person's step without a gate (refused); a waiting step naming an
  unknown id (refused); a cycle (refused); an agent's step with a secret in its command (refused).
- **Pages:** service (AP-4's list), a new specification page for setup steps, conformance (an owner row, a reader row).

## Questions for the requester and the reader

1. Is `title` right as an added member, or does `why` carry the name? Proposed: add `title`.
2. Is the three-gate extension of AP-4's list right, with `secret` and `spend-above-limit` kept as AP-4 names them?
3. Does Fabric Dashboards need anything beyond SS-4 to render a card (an estimate of the wait, which the report's sheet
   mentions)? Proposed: no estimate in the contract; an owner may put it in `why`.

## Not decided here

- Which steps each layer has and in what order: each owner's (the launcher's, the organization product's, the host
  agent's, the PM agent's).
- The setup console's own flow (RM-09) and Fabric Dashboards' card (FD-208, FD-209).
